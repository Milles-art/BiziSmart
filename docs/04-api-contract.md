Headers: `Authorization: Bearer <device_token>`, `Accept: application/json`, `Content-Type: application/json`, optional `Idempotency-Key` on POST /sales.
IDs are prefixed ULIDs (including sale-item IDs used for refunds): `biz_`, `br_`, `usr_`, `prod_`, `bat_`, `cust_`, `sale_`, `till_`, `dev_`, `pay_`, `si_`, `apr_`, `pkg_`, `dep_`, `tce_`. ## Initial owner branch assignment (D103)

`POST /auth/owner/setup` keeps its existing inputs, challenge response, one-use invitation and MFA requirements. Registration assigns the sole active tenant branch only when the new/scaffold owner has no assignment. It preserves an existing assignment and does not guess when zero/multiple active branches exist. No branch input or new endpoint is added. `GET /till-sessions/current` then returns the assigned public branch and `can_open` under the existing till authority; opening still requires the normal explicit request and real opening float. Existing unassigned owners require trusted guarded console repair, not invitation reuse or recovery.

## Envelope
```json
// success
{ "success": true, "data": { }, "meta": { "page": 1, "per_page": 50, "total": 284 }, "request_id": "req_abc" }
// error
{ "success": false, "error": { "code": "INSUFFICIENT_STOCK", "message": "Only 3 units of Bottled Water 500ml available", "field": "items.0.qty", "details": { "available": 3 } }, "request_id": "req_abc" }
```

## Foundation endpoint (S0)
**GET /health** (public, no tenant data) -> `{ "success": true, "data": { "status": "ok", "service": "BiziSmart API" }, "request_id": "req_<ULID>" }`.
This is application liveness only; it does not prove MySQL/Redis, tenant setup or checkout readiness. Browser requests use the same origin via /api/v1; the development Vite proxy forwards /api to local Laravel.

All foundation JSON responses include a server-generated `request_id` and matching `X-Request-Id` header. Client-provided request IDs are not trusted/reused. ## Auth
User-approved browser sessions survive same-tab reload using sessionStorage for `{token,expiresAt,lastActiveAt,deviceUid}` only. A matching device UUID, unexpired token and activity within 30 minutes are required to attempt restore. Restore never supplies user/role/permission data; GET `/me` revalidates the existing device-bound Bearer token before workspace display. Server auth paths and Sanctum contracts are unchanged; no cookie-auth endpoint or public refresh bypass is introduced. Logout, expiry/inactivity and protected UNAUTHORIZED responses remove remembered credentials; reload preserves the original expiry/idle deadlines. No PIN/challenge/TOTP/shop data is persisted. If browser storage is unavailable, access remains memory-only.

Initial owner setup: a local trusted operator runs `bizismart:owner-invite` for an active shop without an operational owner (including inactive/deleted accounts) or approved device. It creates a hashed, one-use, 90-minute invitation and saves the setup link in private local storage. There is no public invitation issuance endpoint. POST `/auth/owner/setup` accepts `{invitation_token,name,phone,pin,device_uid,device_name}` and consumes the invitation under a business lock. It provisions the first owner with a hashed chosen PIN, then returns the normal owner TOTP enrolment challenge; no authenticated token is issued before TOTP verification. Phone/PIN/device validation follows login/staff contracts. Invalid/expired/consumed invitations return 401 `INVALID_INVITATION`; an existing operational owner returns 409 `OWNER_ALREADY_CONFIGURED`. This setup cannot reset an existing owner or bypass TOTP. Setup responses/errors use no-store and never echo credentials. The invitation link uses a browser fragment, removed immediately after reading; tokens are never stored in browser persistence. Super Admin recovery/production onboarding remain separate.
S1 supplies tenant/token infrastructure; S2 now exposes the auth/session/device routes identified below. Staff CRUD, single-use supervisor approval and S4a product catalogue routes are implemented; stock routes remain pending. Tests register private permission probes temporarily. Sanctum cookie/CSRF routes are disabled; tenant APIs use Bearer tokens.

Tenant resolution accepts exactly one subdomain beneath `TENANT_DOMAIN`; unknown/inactive tenants, reserved labels and nested/foreign hosts return the generic 404 envelope. Tenant resolution runs before token authentication and resource binding. Business IDs in headers/query/body never select the tenant. A token for another business returns 401. Resource bindings require the correct prefixed ULID; internal numeric IDs and raw unprefixed ULIDs return 404. Request context and cached guards are cleared after each request, including failures. `/health` remains the only tenant-free API route.

Development uses `TENANT_DOMAIN=localhost`, with frontend shop URLs such as `http://demo-alpha.localhost:15173` proxied to API port 18080. Backend isolation tests configure `bizismart.test`; browser tests use `localhost` against the separate test database. Production uses `bizismart.co.tz`; deployment must explicitly set the domain. No business selector supplies the tenant.

**Users (owner, implemented):** GET `/users?page=1&per_page=50` (maximum 100) -> `{users:[...]}` plus envelope `meta`. POST `/users` accepts `{name,phone,pin,role,branch_id?}` and returns 201 with a managed staff object. `role` is owner/manager/cashier/stockkeeper; PIN is 4–6 digits and is temporary (`must_change_pin=true`). Optional branch ID is an active `br_...` from this shop, or null. PUT `/users/{id}` accepts any of `{name,phone,role,branch_id,is_active}`; PIN changes use the existing reset endpoint, and a submitted PIN here is rejected. POST `/users/{id}/deactivate` returns `{completed:true}` without deleting staff history.

Managed staff objects contain `{id,name,phone,role,branch_id,permissions,is_active,must_change_pin,two_factor_enabled}` with public IDs only. Phone is decrypted only for this owner-only response; PIN/hash/TOTP secrets/internal IDs are never returned. Pagination includes active and inactive non-deleted staff. Responses/errors use no-store. Canonical duplicate phones return 422 VALIDATION_ERROR (field phone), including disabled/deleted reservations; phones in other shops do not conflict. An unavailable/foreign branch gives the same 422 branch_id error. Creation/reactivation counts active staff, including owners, against the plan users limit; null/missing means unlimited. A last active owner cannot be deactivated or demoted (`409 LAST_OWNER_REQUIRED`). Changing profile/branch/role/activation revokes that staff member's tokens/challenges, including self edits; require fresh login. Role assignment replaces old grants. Audit records contain changed field names rather than sensitive profile values.

S2 challenge flow: successful PIN authentication requiring another step returns 202 with `{challenge_token, next_step, expires_at}`. `next_step` is `enroll_totp`, `verify_totp` or `change_pin`. Only enrolment includes `{setup_secret, otpauth_uri}`. Challenge expires in five minutes and has no API permissions. POST `/auth/totp/verify` accepts `{challenge_token, code}` (six digits); POST `/auth/pin/change` accepts `{challenge_token, new_pin}` (4-6 digits, different from old PIN). Each returns the next 202 step or normal 200 token/user response. Errors: `INVALID_CHALLENGE` (401), `INVALID_TOTP` (401), `PIN_CHANGE_REQUIRED` (403), `DEVICE_NOT_APPROVED` (403), `INVALID_PIN` (401), `ACCOUNT_LOCKED` (423), `STAFF_ROLE_REQUIRED` (403). Reset, logout, block and user deactivation return `{completed: true}`. Devices GET returns `{devices:[{id,name,status,user_id,approved_by,last_seen_at}]}` with public IDs only.

S2 backend implementation includes login/challenges, PIN change/reset, logout/rotation, /me, /me/features, owner staff management and device approval/blocking. Supervisor-check is implemented as a narrowly scoped operation approval; it never issues a staff session. These routes require a valid tenant host; protected routes additionally require a bound approved-device token, an active assigned user and no outstanding PIN/owner-TOTP requirement. Role tests still register private product/report probes, which are not production routes. Auth/session/staff/device responses (including errors) use Cache-Control: no-store. Business settings returned by /me are restricted to till_variance_limit; features returns only explicitly stored boolean plan flags (currently empty), without inventing feature tiers. The preserved frontend now calls these real auth/session/staff/device APIs through RTK Query. App does not expose imported synthetic login or prototype shop operations. Stock/till/sales/payment tools remain unavailable until real endpoints exist.

## Products
S4a implements GET/POST `/products` and GET/PUT/DELETE `/products/{id}` with authenticated approved-device sessions and no-store responses. List returns `{products:[...]}` plus envelope pagination metadata. Search, category and current base or active-pack barcode filters are available. Managers/cashiers see active products; users with `manage_products` also see disabled products. Archived/foreign/numeric-ID resources return generic 404.

S5a connects the preserved Products interface to these real routes through live RTK Query. It submits exact quantity strings and integer prices, displays authoritative responses, supports confirmed archive and preserves form values on failure. S4b adds the packaging routes and connected pack forms described below. Stock and payment endpoints remain unavailable.

Create requires name, unit, buying_price and selling_price. Optional quantity_type defaults to `counted`; `weight` requires kg. Prices must be JSON integers within the S3 browser-safe bounds; numeric strings/floats are rejected. Reorder level is an exact quantity string, defaults to `"0"`, and is nonnegative. PUT accepts partial fields, but quantity_type is immutable from creation. Barcode is an optional 1–100-character printable ASCII string without spaces (leading zeros preserved), or null; category is optional text or null. Tracks_expiry defaults false and is_active defaults true. Active product creation/reactivation is checked against plan limits under a shop lock. DELETE returns `{completed:true}` and preserves history and reserved codes.

S4a responses add quantity_type, readonly quantity_precision/quantity_scale and is_active. Until the stock slice is implemented, `stock` and `nearest_expiry` are null and `stock_available` is false. This deliberately supersedes the numeric stock example below for the currently available catalogue. `low_stock` and `expiring_in` remain rejected with 422 VALIDATION_ERROR. S4c accepts nullable department_id and returns department_id/department_name; the department contract is below. Client business_id, stock, internal atom fields, precision/scale and packaging payloads are rejected. Buying price is omitted on all reads without view_buying_price. Changed/archived barcodes remain reserved; collisions return 409 DUPLICATE_BARCODE, even against inactive/history records, while the same code in another shop is allowed. A product may reuse its own historical base code. S4d receiving/batch reads are implemented as defined below; stock adjustments, aggregate catalogue balances and alerts remain unavailable. ## S7 cash checkout
Protected by sell, an approved-device session and no-store on successes/errors. No cash sale is accepted outside the actor's own assigned active branch/open till. Request fields use public IDs and exact quantity strings.

- POST /sales/preview `{branch_id,till_id,items:[{product_id,qty,packaging_id?:null|pkg_...}]}` -> `{branch_id,till_id,lines,subtotal,discount:0,total,vat_rate,vat_amount,review_hash}` plus S22 `margin_warnings` as specified below. Resolves current active prices/packaging and whole items/packages or three-decimal kg. The review writes no sale/stock/cash. Stock is checked at commit, not reserved by a review.
- POST /sales requires UUID Idempotency-Key and `{branch_id,till_id,items,cash_tendered,review_hash}`. S9 additionally permits optional customer_id/credit_amount as specified below. Requests reject arbitrary payments, discount, approval_token and total, including nested item fields outside product_id/qty/packaging_id. Same key/actor/device/body returns original immutable sale with replayed:true (200); first completion returns replayed:false (201). Changed use of a key returns OPERATION_ID_REUSED (409). Missing/malformed keys fail VALIDATION_ERROR (422).
- Commit re-resolves/locks actor, token/device, shop, explicit till, products and eligible batches. Review hash mismatch returns SALE_CHANGED (409); inactive products PRODUCT_INACTIVE (409), obsolete/ineligible packaging PACKAGING_VERSION_CHANGED (409), insufficient eligible stock INSUFFICIENT_STOCK (400, details product_id and available_qty), insufficient cash PAYMENT_MISMATCH (400). Foreign product/pack IDs never resolve; a foreign/missing till gives TILL_REQUIRED (400); another staff member's till/branch gives PERMISSION_DENIED (403). Closed till gives TILL_CLOSED (409). No partial stock, sequence, sale, payment or cash journal survives a failure.
- Result `{id,receipt_number,status,branch_id,cashier_id,till_id,subtotal,discount,total,vat_rate,vat_amount,cash_tendered,change_given,lines,items,payments,receipt_url:null,created_at,replayed}` plus S22 `margin_warnings` on fresh commits (omitted on idempotent replays) as specified below. Lines are immutable logical-price snapshots `{product_id,name,quantity_type,unit,qty,base_qty,packaging_id,packaging_name,packaging_version,conversion_atoms,unit_price,discount:0,line_total}`. Sum line_total from lines. Per-batch items `{id:si_,product_id,batch_id,line_index,base_qty,unit_price}` identify stock allocations; base_qty does not mean package count and batch rows must not independently recalculate charges. Payments `{id:pay_,method:'cash',amount:total}` record net cash; change_given is tendered minus total. Costs/internal IDs are omitted.
- GET /sales/{sale} returns the saved snapshot to its originating cashier/device under sell. Owner report receipt reads use the separate `GET /reports/sales/{sale}/receipt` endpoint below; the cashier/device restriction on this route is unchanged. The inline UI receipt is available after commit; signed PDF receipt lookup/job remains S8. Other sales list/hold/refund/mobile APIs above remain unavailable. Credit uses the S9 extension below.

Server allocation applies D076: dated eligible stock (expiry/id) before undated eligible stock (received_at/id). Lines use one product base balance regardless of package; rounding happens before allocation. All money has the existing browser-safe bound. Cart and uncertain operation are in-memory only, survive screen navigation, and clear on logout; the UI warns on reload during uncertainty. No new local/session storage fields are introduced.

## S22 margin alerts (F10.12, warn-only)
Sale preview and fresh sale commits include `margin_warnings`, bound by the same `review_hash`. Each quoted line is split across its actual quoted batches (pricing allocations, or a read-only FEFO projection when no pricing rules apply); each segment's final customer-paid net (after automatic offers, line/cart discounts and loyalty) is compared with that batch's recorded `cost_price` share (`Money::lineTotal` atoms math, so split-batch sales use actual costs and weighted goods use exact grams). Entries with net strictly below cost: `{code:MARGIN_BELOW_COST,line_index,product_id,product_name,batch_id,batch_number,base_qty,net_total}`. Audience: actors with `view_buying_price` (owners) additionally receive integer `cost_total`/`shortfall`; actors with `approve_variance` but no cost view (managers) receive the redacted entry with no cost figures; cashiers receive no `margin_warnings` key at all. Warnings never change prices and never block or approve a sale; optional margin blocking/override policy remains undecided (D023/D090) and is not implemented. POS review and fresh receipt dialogs display these server values through MarginWarnings.tsx, remain non-blocking and omit cost fields whenever Laravel omits them. Customer display and printed receipt projections exclude margin warnings and costs.

## Till (S6)
All routes require manage_till and a full approved-device session; responses/errors are no-store. Owners list all tenant branches, managers their assigned branch and cashiers their own sessions. All writes act on the authenticated staff member's own assigned-branch till. Internal IDs never leave the API.
- GET /till-sessions/current -> {till:null|Till,branch:null|{id,name},variance_limit,can_open}. No assigned active branch disables opening.
- GET /till-sessions?status=open|closed&page=1&per_page=10 -> data.tills and meta {page,per_page,total,owner_review_count}. Owner review count includes closed above-limit variances across the business regardless of list filter; managers/cashiers receive zero. The owner sees a persistent review notice in Tills & Cash; external notifications remain pending messaging infrastructure.
- POST /till-sessions/open {operation_id:UUID,branch_id:br_,opening_float:integer TSh} -> 201 {till,replayed:false}. One open per business/branch/cashier; TILL_ALREADY_OPEN 409. Concurrent open capacity is business-wide (D070); PLAN_LIMIT_REACHED 403. A missing/invalid plan limit fails closed; explicit null means unlimited. Zero opening float is valid.
- POST /till-sessions/current/paid-out {operation_id:UUID,till_id:till_,amount:positive integer TSh,reason:string max500} -> 201 {till,entry_id:tce_,replayed:false}. The explicit target prevents a retry affecting a subsequent shift. Reason is encrypted; audit omits it. A paid-out is an expense cash deduction, separate from a cash drop.
- POST /till-sessions/current/close {operation_id:UUID,till_id:till_,counted_cash:integer TSh,approval_token?:null|64-hex} -> 201 {till,replayed:false}. **Blind close:** clients never send expected_cash/revision/variance_limit (they are `prohibited`); the server owns the review. The retry carries the bound approve_variance grant (see supervisor-check below), which must match the server-recomputed snapshot at consumption (else INVALID_APPROVAL, unconsumed). Owner approval requires fresh TOTP, managers require matching branch. Closed till is immutable; new paid-outs/cash entries/closing operations return 409 TILL_CLOSED.
- Blind read surface: for an **open** till, `Till.expected_cash` is `null` for cashiers (own `/current` and overview rows); managers/owners receive the live figure (their X view). Closed tills always expose their immutable expected cash.
Matching retries of any committed operation return 200 with its original encrypted stored result and replayed:true, including after a later shift opens or a grant expires/is consumed. Changed type/fields/actor/device under the same business operation ID return 409 OPERATION_ID_REUSED. Clients retain the same exact operation on network/408/5xx uncertainty, and remove credentials/grants from mutation caches.
Till resource: {id,branch_id,branch_name,cashier_id,cashier_name,status,opening_float,expected_cash,closing_cash,variance,revision,opened_at,closed_at,approved_by,owner_review_required}. ## Single-use supervisor approval (S2 implementation)
POST `/auth/supervisor-check` requires the requester's full device-bound staff token and accepts `{phone,pin,permission,operation_id,payload_hash,code?,till_id?,counted_cash?}`. `phone` identifies the supervisor using canonical Tanzania format; PIN is 4–6 digits. `permission` is limited to `refund`, `void`, `give_discount`, `approve_variance` or `adjust_stock`. `operation_id` is a UUID identifying one domain operation. `payload_hash` is a lowercase SHA-256 digest of the exact reviewed operation snapshot, including targets, quantities, integer TSh amounts, reason and relevant settings/version. For a blind till variance the closer also sends `till_id` + `counted_cash` (required together): the server recomputes the closing review server-side under the requester's own-till authority **after the approver has authenticated**, binds the grant to that fresh hash instead of the client digest, and adds `review:{counted_cash,expected_cash,variance,variance_limit}` to the response - the approver is the first party to see the numbers. For adjust_stock the approver must be an owner; other actions allow an owner/manager with that permission. A supervisor must be active, a completed PIN change and no account lock. Owners additionally require confirmed TOTP and a fresh six-digit `code`; approval never enrols or recovers an owner.

Response 200: `{approved_by:"usr_...",approval_token:"<64 hex secret>",expires_at:"<UTC ISO8601>"}` plus, for a bound till variance, `review:{counted_cash,expected_cash,variance,variance_limit}`. No login token or broad permission grant is returned. Approval lasts five minutes, is hashed in the database and is bound to the current business, requester, Sanctum session, device, permission, operation UUID and payload digest. A replacement for the same session/operation/permission invalidates older unused grants. Response/errors use no-store. Never persist approval secrets in browser storage or expose them in logs.

Requester needs `adjust_stock` for correction approvals, `sell` for refund/void/discount approvals or `manage_till` for a variance approval; this endpoint does not give them that permission permanently. Unknown/disabled/wrong supervisor credentials return the same 401 `INVALID_PIN`. Failed PIN attempts share login's five-failure/15-minute persisted lockout. Issuance uses the existing canonical phone+IP+business 5/min and IP+business 60/min limiter. Unsupported actions, malformed UUIDs/digests or code return 422 `VALIDATION_ERROR`. Ineligible supervisors return 403 `APPROVER_NOT_AUTHORIZED`; an owner without a supplied code returns 403 `TOTP_REQUIRED`; invalid/replayed codes return 401 `INVALID_TOTP`.

Consumption is an internal `SupervisorApprovalService::execute` call, not a public consume endpoint. The implementing refund/void/discount/till service must resolve and lock its tenant resources within its outer DB transaction, validate its full operation, derive the authoritative snapshot, and provide that snapshot to the approval service. It must never echo `payload_hash` from the client as proof or bypass stock/till/domain permissions. Snapshot hashing recursively sorts object keys, preserves array order, uses compact UTF-8 JSON with unescaped Unicode/slashes, and accepts exact integer/string/bool/null scalars, never floats. The server-reviewed hash should be supplied by the domain preview when that workflow is built.

Consumption revalidates active roles/permission, completed PIN change, account lock, current unrevoked/unexpired requester session and approved device. It checks the exact binding under row locks, marks the approval consumed before executing the domain DB callback, and audits issuance/consumption without PIN/token/profile data. The approval and domain DB changes commit or roll back together; recursive/duplicate use fails. No external provider calls may run inside the retried DB callback. Expired, consumed, replaced, foreign, changed-operation/snapshot/session or ineligible approvals return 403 `INVALID_APPROVAL` (session revocation returns normal 401). Profile/role/PIN/activation changes revoke associated grants; requester logout/rotation/device blocking deletes them through the session relationship.

Stock correction endpoints/owner approval are implemented by S4g, and till closing consumes variance grants in S6; sale/refund consumers remain future tasks; this foundation does not process a sale or refund, and does not enable currently unavailable screens. Production owner recovery and manager department resource scope remain separate decisions; D071 defines till branch scope below.
Frontend RTK Query exports useSupervisorCheckMutation for future domain dialogs. They must remove the mutation result after each attempt and retain the returned grant only in transient operation state. The adapter preserves the requester's session for supervisor INVALID_PIN/INVALID_TOTP failures; UNAUTHORIZED or other unexpected protected 401s still clear credentials/cache. This distinction does not turn failed approvals into successful actions.

Saved line_total is final net value; subtotal is the sum after line reductions before the cart discount. Held routes: GET/POST held-carts, POST held-carts/{hold}/resume and DELETE held-carts/{hold}, all approved-device sell, branch scoped, no-store, UUID bound and no financial effect. See F03-held-carts.

Multipart image and expected_revision implement optimistic replace/remove. ProductResource exposes only nullable revision/mime/bytes/dimensions metadata; no private paths or public file URLs. Missing private R2 configuration fails explicitly.
Price tools: GET products/{product}/price-history and /shelf-labels under manage_products, tenant scoped and no costs. History records start with this feature, including initial/change/package-version snapshots; older changes are not fabricated.

## Coordinated operations API (D087/D088)

All paths below are relative to `/api/v1`; normal endpoints require approved-device staff authentication, tenant hostname resolution and private no-store responses. Laravel owns prices, stock, authority and totals. Write bodies use immutable operation UUIDs; uncertain clients retain the same UUID and body. No body may select a business.

- Suppliers: owner `GET /suppliers`; authorised stock receiving `GET /supplier-receiving`; `POST /suppliers/actions/{supplier|order|receive|payment|return|credit|apply_credit}/preview` and matching commit. Owner-issued orders constrain keeper receiving; bank/mobile payment records attest completed external payments and do not initiate transfers.
- Expenses: owner `GET /expenses`, `POST /expenses/preview`, `POST /expenses`; nested `/{expense}/reverse/preview`, `/reverse`, `/payments/preview`, `/payments`. Recording/reversal/payment commits require their server review hash. Till-funded payments require bound owner `manage_settings` approval and own open till. External payments/refunds retain original source and completed reference. Reversals do not pretend paid funds have returned.
- Expense photos: owner `GET /expenses/attachment-capabilities`; nested `/{expense}/attachments` list/upload and `/{attachment}` authenticated content/delete. Upload uses multipart `operation_id` and `image`; validated JPEG/PNG/WebP bytes, 2 MB, up to 4096 pixels per side, maximum twenty photos. Unconfigured private storage remains unavailable.
- Reports: owner `GET /reports/summary`, `/sales`, `/stock` with inclusive Tanzania `from`/`to`, bounded periods and paginated ledgers. Accrual summary distinguishes revenue, saved VAT, original COGS, reversals, recorded expenses and commission accrual. `profit_before_commissions` and `net_profit` are explicit; payouts affect cash flow once. Stock valuation is current as-of stock, with held and negative conflicts separate. CSV export uses these server results and escapes spreadsheet formulas.
- Cash drops: `GET /cash-drops/receivers`, `/cash-drops`; `POST /cash-drops/preview`, `/cash-drops`, nested `/acknowledge`, `/reverse`. Handover preview binds drawer revision and receiver; pending drops block close. Acknowledgement changes no money and requires current receiver/branch authority even on replay. Owner reversal requires confirmed actual cash return and open original drawer.
- Pricing: owner `GET /pricing/rules`, `POST /pricing/rules/preview`, `/pricing/rules`; nested `/{rule}/cancel/preview` and `/cancel`. Types schedule/fixed/percentage/buy-get/markdown share exact server checkout allocations. One best automatic offer precedes approved manual/loyalty discounts. Exchange replacement uses scheduled base prices and excludes conditional automatic offers through a server-only transaction boundary.
- Staff operations: `GET /staff-operations`; `POST /staff-operations/{clock_in|clock_out|correction|preferences|read_notification}`. Self attendance/preferences are available to authenticated staff; owner corrections bind revisions and retain original stamps. WhatsApp/SMS preferences do not claim delivery while providers are unconfigured.
- Incentives: owner configuration preview/commit under `/incentives/configuration`; commissions, external payout preview/commit and historical forecasts under `/incentives`. Customer-scoped `/customers/{customer}/loyalty` requires customer-management authority. Checkout accepts `loyalty_points`; the approved discount is bound to actual customer balance and configuration, consumed atomically with stock, sale, payment and earning records. Returns restore spent points proportionally and allow negative earned-point carry.
- Offline: authenticated `POST /offline/leases` requires own open till. The response returns an encrypted-cache-ready catalogue, public cashier ID and signing secret for one tenant/device/user. `POST /offline/sync` authenticates the entire immutable body through `X-Offline-Signature` HMAC, not browser identity or an unrelated Bearer token. Body fields: lease_id, device_uid, operation_id, captured_at (ISO UTC milliseconds), cash_tendered and items[{snapshot_id,proof,qty}]. Legitimate stock/price/expiry conflicts commit and flag; authority/closed-till issues persist in quarantine. Owner `/offline/quarantine`, nested `/preview` and `/reconcile` require real own reconciliation drawer and bound approval. Reconciliation preserves original actor/branch/capture and closed till. Local logout blocks new capture while retaining encrypted unsynced operations; server logout, PIN/authority/device changes revoke leases.

Language preference changes presentation only: API enum values, IDs, fingerprints and monetary snapshots remain unchanged. Missing credentials do not trigger simulated success.

## Coordinated remaining-software contract (F17–F20)

All staff endpoints below use `/api/v1`, the established envelope and private/no-store responses. IDs are public prefixed identifiers, quantities are exact strings and money is an actual JSON integer within the existing browser-safe TSh range; amount strings/floats are not accepted. Tenant authority always comes from the request context. These implemented contracts do not establish external credentials, hardware compatibility, migration deployment or final acceptance; final executed checks belong in the handoff.

### F19 department/till reports, stock loss/counts and alerts

- Owner + `view_reports`: `GET /reports/departments?from=YYYY-MM-DD&to=YYYY-MM-DD`, optional `department_id`/`branch_id`. Returns department rows, `classification: current_product_department`, stock scope, period and as-of timestamp. Revenue/VAT/refunds/original COGS are journal-derived; stock is current business-wide valuation, with negative conflict batches flagged/excluded. This is explicitly current-assignment classification, not sale-time department attribution.
- Same owner authority: `GET /reports/tills`, dates, optional branch, `page`/`per_page` (maximum 100). Returns sessions overlapping the period and normal pagination meta. `period_cash_entries`/`period_cash_drops` cover selected-date journals; opening float/expected/count/variance cover the full session. Drops remain internal transfers, not expenses.
- `adjust_stock`: `POST /stock/losses/preview` takes `{operation_id,batch_id,qty,category:damage|spoilage|wastage,reason}`. `POST /stock/losses` adds reviewed `expected_qty` and `approval_token` when required. Quantity is a positive base-unit string. Preview returns `snapshot`, `payload_hash`, `qty_after`, `approval_required` and integer `loss_value`; commit returns public `movement`, immutable `loss` snapshot and `replayed` (201 first, 200 replay). Every stockkeeper commit requires the existing bound owner grant; owners write directly.
- `adjust_stock`: `POST /stock/counts/preview` takes `{operation_id,department_id,batch_id,qty,reason}`, where qty is the non-negative physical count. `POST /stock/counts` adds expected balance/approval. Laravel computes the signed variance, verifies current department assignment and writes one `stock_count` movement even at zero variance. Review/commit use the same correction envelope; changed department/balance returns `DEPARTMENT_CHANGED`/`STOCK_CHANGED`.
- Owner + `view_reports`: `GET /reports/losses`, dates, optional snapshot `department_id`/category and pagination. Returns `losses`, integer totals by category, record count and `basis: classified_stock_loss_movements_only`, with top-level meta. General corrections, counts, damaged customer returns and supplier returns are not duplicated as losses. Summary `stock_loss_cost` subtracts classified loss costs once; branch-only summaries do not invent branch attribution for physical stock.
- Owner + `view_reports`: `GET /loss-alerts` returns persistent alerts/configuration/meta; `PUT /loss-alerts/configuration` takes all three nullable `refund_count`, `refund_amount`, `void_count` thresholds. Enabled values are positive integers (counts at most 10,000); null disables independently. `POST /loss-alerts/refresh` evaluates the current Tanzania day and returns new count. `POST /loss-alerts/{alert}/acknowledge` idempotently acknowledges tenant-owned evidence. Threshold crossings deduplicate by staff/kind/day and do not prove external notification delivery.

Report dates share the inclusive Tanzania range contract, maximum 366 days. Unknown/foreign resources return generic not-found; calculated costs/changes/approvers and `business_id` cannot be supplied as authority. See F19 for exact row fields and classification boundaries.

### F18 bank reconciliation and supplier planning

Owner-only `GET /banking` returns `{lines,payments,schedules,external_transfer_executed:false}`. Lines contain public ID, private account label/reference, booking date, direction, integer amount and nullable matched public payment ID/type. Candidates are already recorded bank supplier/expense payments; expense refund candidates are credits. Schedules include public invoice/reference/supplier attribution, planned date/amount, current unpaid amount, status and overdue flag.

`POST /banking/{statement|match|schedule|cancel}` takes UUID `operation_id` in the body and the relevant fields:

- `statement`: `{account,booked_on,direction:debit|credit,amount,reference}`; account at most 100 characters, reference 2–150 characters, date `YYYY-MM-DD`, positive integer amount. Account/reference identity is unique; duplicate evidence returns `REFERENCE_ALREADY_RECORDED`.
- `match`: `{line_id,payment_type:supplier|expense,payment_id}`. Only one-to-one, exact same amount/direction and already completed bank-source records can match. Mismatch returns `BANK_MATCH_MISMATCH`; either side already matched returns `BANK_ALREADY_MATCHED`. No balance/till/payment journal changes and no bank transfer occur.
- `schedule`: `{invoice_id,due_on,amount}`; positive planned amount plus existing active plans cannot exceed the selected current unpaid invoice (`PAYABLE_CHANGED`). A plan is an advisory reminder, not cash reservation or automated payout. Current unpaid amount remains separate after later payments/credits.
- `cancel`: `{schedule_id}` retains the cancelled plan. Overdue means an active plan before today's Tanzania date on a currently unpaid invoice.

Writes return their public `line` or `schedule`, `external_transfer_executed:false` and `replayed`. Immutable tenant/actor/device UUID fingerprints make identical uncertain retries safe; changed bodies return `OPERATION_ID_REUSED`. `GET /supplier-price-comparisons` returns historical last-three received cost observations per exact product/base unit, newest invoice date/ID first, in TSh per base item or kilogram. These are receipt costs rather than current quotations. Bank feeds, vendor statement imports, inferred fees/adjustments, many-to-one matching and automatic transfers are not implied.

### F17 customer display, scale labels, QR cards and leaderboard

The customer display has no new API or persistent pairing record. It is a same-computer sanitized browser popout: draft product names/public quantity/unit only, then authoritative Laravel-reviewed charges/totals. It omits customer/staff/private data and never reports payment success; cart clear/unmount/sign-out clears or closes it. Independent tablets and direct hardware transports need separate verified device contracts.

- `sell`: `GET /scales/profile` returns `{profile:null|configured-fields,format:ean13_weight_grams,hardware_verified:false}`. Owner + `manage_settings`: `POST /scales/profile` takes `{operation_id,profile}`; null disables. A profile has numeric-string `prefix` (1–4 digits), zero-based `product_start`, `product_length`, `weight_start`, `weight_length`. Nonempty segments must fit in the first 12 digits and be mutually disjoint from the prefix; final EAN-13 digit remains the check digit. Configuration UUID replay is actor/device/input bound.
- `sell`: `POST /scales/decode` takes `{label:"13 digits"}`. Laravel validates profile/check digit/prefix and nonzero integer grams, preserves product-code leading zeros and resolves an active weighed product's exact base barcode. Returns existing permission-filtered `product` and canonical kg `qty`. No price/stock is taken from the label; normal checkout remains authoritative. Embedded-price labels and USB/serial/Bluetooth/tare/calibration protocols are not implemented or certified.
- `manage_customers`: `GET /customers/{customer}/loyalty-card` returns `{card:null|{id,token,active,created_at}}`; `POST` takes `{operation_id}`, issuing/replacing an encrypted random `BSL:` token (201 first, 200 replay). Replacement atomically revokes old cards. Replaying a superseded issuance returns inactive/null-token status rather than reviving it.
- `manage_customers`: rate-limited `POST /loyalty-cards/resolve` takes `{token}`, returns the established CustomerResource and cannot resolve foreign/revoked cards. A card selects a customer; it authorizes neither sign-in nor spending. Existing points/credit/redemption services remain authoritative. QR generation/printing happens locally without an external token service.
- Owner + `view_reports`: `GET /incentives/leaderboard?page=1&per_page=30` (1–100 page size) returns `leaderboard`, `basis: all_time_net_earned_commission` and top-level meta. Original-cashier net earned commission after reversals determines competition rank; ties share rank and public IDs deterministically order them. Payouts do not alter earned rank or imply wages/bonuses.

### F20 WhatsApp/SMS delivery

Owner-only `GET /messaging` returns paginated capabilities, automation settings and delivery status fields (`id,channel,purpose,status,failure_code,accepted_at,delivered_at,created_at`), never message content/phone or raw provider responses. `GET /customers/{customer}/message-consent` requires `manage_customers` and returns channel/purpose booleans plus revision.

`POST /messaging/{consent|receipt|debt_reminder|automation}` requires `manage_customers` and UUID `Idempotency-Key`; request business/recipient/message overrides are prohibited. Immutable actor/device fingerprints preserve uncertain retry. Action fields:

- `consent`: `{customer_id,expected_revision,whatsapp,sms,receipts,debt_reminders,evidence}`. Explicit evidence is encrypted and revision protected (`CONSENT_CHANGED`).
- `receipt`: `{customer_id,sale_id,channel:whatsapp|sms}`. Original receipt/customer identity and current branch/cashier authority are checked; explicit channel and receipt-purpose consent plus a phone are required (`MESSAGE_CONSENT_REQUIRED`, `RECEIPT_CUSTOMER_MISMATCH`).
- `debt_reminder`: owner-only `{customer_id,channel}`; explicit channel/reminder consent required. No custom recipient/message or sale ID accepted.
- `automation`: owner-only `{expected_revision,daily_summary,debt_reminders,at_time:HH:mm,renewal_days:null|1..90}`. Revision protected (`AUTOMATION_CHANGED`); daily summaries, automatic customer reminders and renewal notices start disabled. Source receipt/channel and customer/Tanzania-day reminders deduplicate separately from UUIDs.

`messaging:dispatch` runs explicit tenant contexts, rechecks current consent/phone/recipient authority/features/subscription, and sends outside transactions only after claiming a journal row. Missing credentials block with `PROVIDER_NOT_CONFIGURED` without a network request. Queued/blocked records older than one day are cancelled with `MESSAGE_EXPIRED`. States distinguish queued, blocked, dispatching, accepted, delivered, failed, uncertain and cancelled. Transport uncertainty/abandoned three-minute claims and duplicate provider IDs never automatically resend; conflicting IDs become `PROVIDER_ID_CONFLICT`. Acceptance is not proof of delivery.

`GET /messaging/whatsapp/webhook` verifies Meta subscription token/challenge. `POST` on the same public callback requires body HMAC `X-Hub-Signature-256`, configured business mapping/phone-number ID, bounded payload and known delivered/read/failed statuses. Authenticated early status evidence persists before provider-ID mapping and applies under lock once the send result arrives; callbacks are deduplicated and delivered state cannot regress. `messaging:reconcile-sms` uses the verified fixed Beem HTTPS GET report API with Basic authentication, original destination/request-ID matching and durable five-minute read claims. Documented `DELIVERED`/`UNDELIVERED` evidence updates only still-accepted matching records; pending/unknown/error evidence never implies delivery, and no message is resent. SMS sends use integer recipient reference 1 and documented GSM encoding 0; unsupported text is blocked/`SMS_ENCODING_UNVERIFIED` before HTTP because the provider Unicode selector remains unverified. See F20-sms-delivery-reports. Private configured Meta utility template/language/token/phone/secret/public HTTPS and Beem sender/credits/key/secret plus real send/report/Unicode/multipart behavior must be verified externally; configuration is scoped to one business. No provider credential, real message delivery or external acceptance is implied by local tests.

### Explicit completed-void extension

Existing `POST /returns/preview` and `POST /returns` additionally accept optional `operation_kind: return|void`. Omitted ordinary-return snapshots/fingerprints remain compatible. `void` requires every remaining original base quantity/line and cannot include `replacement`; partial/omitted lines return `VOID_QUANTITY_REQUIRED`, exchange attempts `VOID_EXCHANGE_UNAVAILABLE`. Explicit void intent is part of the authoritative review/supervisor snapshot, so changing it after approval rejects as `RETURN_CHANGED`. Existing refund approval, debt-first allocation, stock/quarantine and completed external mobile-refund rules remain unchanged. The committed normal return additionally records one `sale_voided` audit; retries cannot duplicate it. Ordinary full refunds are not inferred as voids. See F03-completed-void-audit.

## F21 enterprise API (read-only integrations)

Owner-issued headless credentials for a shop's own systems. All paths are `/api/v1/enterprise`, standard envelope, `no-store`, public IDs, integer TSh, exact quantity strings. Collection pagination follows the reused controllers (maximum 100 for product/department/stock/report collections, maximum 50 for tills, fixed 50 for packagings), with top-level `meta` where supplied. Product details, aggregate summaries and token metadata lists are not paginated. No write endpoint exists; mutations remain interactive staff workflows. See F21.

- Owner staff session: `POST /enterprise/tokens` `{name, expires_in_days?: 1-365 (default 90)}` returns `{id: tok_ULID, name, abilities: ["enterprise:read"], token, expires_at}` (201). Plaintext appears once and is never stored or listed. `GET /enterprise/tokens` lists metadata only. `DELETE /enterprise/tokens/{token}` revokes immediately (200 `{revoked:true,id}`); revoked tokens authenticate as 401. Non-enterprise token ids return 404.
- Integration reads require the explicit `enterprise:read` ability plus owner role plus `throttle:enterprise` (120/min per business+token; excess is `RATE_LIMITED` 429). Interactive `*` staff tokens are rejected (403 `PERMISSION_DENIED`); unsigned/foreign tokens are 401. Disabled `api_access` or the underlying module flag returns 403 `FEATURE_DISABLED`. Dedicated headless keys must have exactly the enterprise ability, no device and a future expiry; the current sole owner must be active, have no pending PIN change and have confirmed TOTP. Token management refreshes interactive token/device authority inside its transaction.
- `GET /enterprise/products|/products/{product}|/products/{product}/packagings|/products/{product}/batches|/products/{product}/movements`, `/enterprise/stock/reorder-alerts|/expiry-alerts`, `/enterprise/reports/summary|/sales|/stock`, `/enterprise/departments`, `/enterprise/till-sessions`. They reuse the staff controllers/services, so buying prices appear only as the owner's own data. Excluded by design: customers/debt (PII), payments, staff, devices, messaging, pricing configuration and all writes.

## Production readiness

Public `GET /api/v1/ready` is tenant-free and returns the standard envelope with `{ready:boolean,checks:{database:boolean,migrations:boolean,cache:boolean}}`; status is 200 only when all checks pass, otherwise 503. Database connectivity, a nonempty readable migration source with no pending migrations, and fresh shared application-cache/rate-limiter write/read probes are required. Array/file/null/failover stores cannot establish readiness. No connection values, versions, migration names, keys or exception details are exposed. It does not certify workers, scheduler, providers, R2, backups or hardware. Enterprise and readiness responses/errors explicitly use `Cache-Control: no-store, private`, including failures before route middleware. Liveness remains `GET /api/v1/health`.

D102 platform clarification: completed subscription payment paid_on remains a Y-m-d date and must be on or before today in Africa/Dar_es_Salaam, including the local-midnight/UTC-previous-day window. No field, endpoint, payment-execution or idempotency contract changed.

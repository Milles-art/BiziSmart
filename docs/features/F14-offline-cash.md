# Signed offline cash capture and recovery

The D087/D088 operations batch permits cash-only offline counter sales under a server-issued 24-hour lease. Normal sign-in and workspace permissions still require Laravel; an offline lease never restores normal browser authentication. Preparing a lease requires an approved device, an active authorised cashier and their own open till. The server binds the tenant, cashier, device, till, VAT and cached catalogue snapshots. Cached regular/scheduled prices apply; conditional automatic offers, manual discounts, credit, mobile payments and returns require a connection.

Each cached product/pack has an immutable snapshot ID and server proof of its quantity type, version, conversion and price. Sync accepts no client-supplied business, prices, VAT or calculated totals. The tenant comes from the hostname and the persisted lease supplies the actor/device. The client signs the SHA-256 hash of exact canonical JSON with HMAC-SHA256 using the lease secret; PHP and Web Crypto share a known-vector test. Laravel quotes the trusted snapshot again, owns the financial totals and enforces immutable UUID/body recovery.

Dexie stores only AES-GCM ciphertext for the necessary catalogue and sale queue. Non-exportable CryptoKeys remain in IndexedDB; record ID, tenant/device/user scope and kind are authenticated associated data. No PIN, TOTP secret, challenge, browser permissions or unrelated customer data enters offline storage. Every sign-out cause revokes capture immediately, removes cached catalogues and confirmed local receipts, and preserves unresolved encrypted queues with their recovery keys. Reload recovers the same operation. Storage/crypto failure never returns simulated success, and an incomplete server response never confirms a sale.

Signed counter sales commit at their cached price and original event date. Depleted, expired, recalled/quarantined batches and changed current prices are accepted with owner-visible conflicts; every allocation still passes through StockService and writes the stock movement, original batch-cost allocation and cash journal in one transaction. Revoked/expired leases, changed staff authority, closed tills or invalid trusted snapshots are durably quarantined. Unknown or unauthenticated leases cannot authorise server writes; their local queues remain recoverable.

Owners review quarantined evidence and select their own open reconciliation till, obtain a bound owner approval, and post the reviewed cash atomically. The original cashier, device, branch and event time remain recorded; the original closed till is immutable. Replays do not duplicate stock, sales, approvals or cash. Invalid financial evidence stays quarantined rather than silently being edited into a sale.

Endpoints: `POST /offline/leases`, lease-authenticated `POST /offline/sync`, owner-only `GET /offline/quarantine`, `POST /offline/quarantine/{offlineOperation}/preview` and `/reconcile`. All use the existing JSON envelope and private no-store responses. The connected UI exposes preparation, provisional exact cash display, encrypted capture, signed synchronisation, genuine receipts after server confirmation and owner reconciliation. Capture/read scope never crosses tenant, device or cashier.

Verification covers PHP/Web Crypto signatures, exact gram/package displays, encrypted-key/ciphertext recovery and tamper failure, logout preservation, identical local retries, no unrelated Bearer token in sync, language/cart preservation, real API tenant/replay/stock/expiry/revocation/closed-till/rollback cases, and native IndexedDB desktop/phone reload/logout acceptance. Final counts and completion gates live in the main operations evidence.

# Platform administration and WhatsApp/SMS delivery

Implements F07 and D089. Local software and external production verification are distinct gates.

## Platform

Filament 5 at `ADMIN_DOMAIN` uses separate `admin_users` and an admin session guard, required authenticator MFA, encrypted secrets, transactional persisted TOTP timestep replay prevention and 30-minute idle expiry. Tenant Bearer tokens cannot authenticate the panel. Optional IP allowlisting and host-only encrypted admin cookies apply to persistent Livewire requests. Create the first administrator interactively with `php artisan bizismart:admin-create`; credentials never appear in command arguments/output. Operator credentials are not provisioned by this batch.

The panel manages explicit plan features, clients, subscription terms and immutable completed-payment records. Mutations refresh administrator authority under locks and store encrypted actor-bound operation results. Onboarding atomically creates the business, default roles, main branch and selected subscription. A private 90-minute one-use setup link opens the existing owner-selected PIN/TOTP flow; it never resets an operational owner. Subscription ends are exclusive Tanzania midnight boundaries chosen by the operator. No grace period, automatic renewal or payment transfer is inferred.

Baseline plans can be created without overwriting existing plans: Free TSh 0, Basic 70,000, Professional 150,000, Enterprise 280,000. Existing active usage blocks limit reductions. New baseline features start explicitly false until assigned by admin; additions are not silently assigned to tiers. Existing local shops without managed subscriptions/flags keep existing functionality until explicitly managed. `/me` and `/me/features` return effective flags; Pennant re-evaluates scoped plan/override rows. Disabled mapped endpoints return `FEATURE_DISABLED`; inactive managed terms return `SUBSCRIPTION_INACTIVE`. Authentication and read-only `/subscription-status` stay available. TRA cannot be enabled; lost-owner-authenticator recovery remains disabled by user decision.

## Messaging

`GET /messaging` is owner-only and paginated; it returns capabilities, automation configuration and statuses without recipient/message content. `GET /customers/{customer}/message-consent` requires `manage_customers`. `POST /messaging/{consent|receipt|debt_reminder|automation}` requires UUID `Idempotency-Key`; actor/device fingerprints freeze replay inputs. Recipient/message/business overrides are prohibited. Consent binds owned customer, channel/purpose booleans, expected revision and encrypted explicit consent/revocation evidence. Receipt delivery checks original customer and current branch/cashier authority. Debt reminders/automation configuration are owner-only. Source receipt/channel and customer/Tanzania-day reminder keys deduplicate independently of operation UUIDs.

Owner alerts reuse authorised in-app notices and configured loss alerts. Optional owner-selected daily time controls previous-day summaries and consented customer debt reminders. Renewal days are nullable. These three automations start disabled; opted-in owner event notices retain their existing preferences. `messaging:dispatch` generates notices in explicit tenant contexts, claims records transactionally, rechecks current consent/phone/authority/subscription/features, and performs one HTTP call outside the DB transaction. Abandoned three-minute claims become uncertain and are never automatically resent.

States: queued, blocked, dispatching, accepted, delivered, failed, uncertain, cancelled. Provider acceptance is never delivery. Signed Meta evidence can mark known WhatsApp IDs delivered; HMAC, phone-number binding, tenant mapping and monotonic statuses are required. SMS now uses the verified authenticated Beem GET report contract with exact original request-ID/recipient matching and durable five-minute polling; real provider send/report verification remains external. Missing configuration leaves blocked records and makes zero network calls. Phones/message/consent evidence are encrypted; raw provider responses/secrets are neither returned nor logged. Browser pending operations remain in memory and clear on sign-out. See F20-sms-delivery-reports for source links, status semantics and the GSM/unsupported-Unicode boundary.

Meta configuration requires an approved utility template with exactly one BODY text parameter, approved language, selected supported Graph version, phone-number ID, token, app secret and public HTTPS signed webhook. Beem requires approved sender, account credits and Basic key/secret; TLS verification stays enabled. Credentials are privately bound to a single business public ID. Other tenants remain unconfigured.

References: [Filament required MFA](https://filamentphp.com/docs/5.x/users/multi-factor-authentication), [Meta official Cloud API examples](https://github.com/fbsamples/whatsapp-api-examples), [Beem official SMS request example](https://beem.africa/sms-api/). Sandbox/template/sender verification is still external work.

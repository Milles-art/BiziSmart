## Authoritative behaviour

- Department financial reports require owner + `view_reports`. Receipt revenue uses immutable logical line totals, stored output VAT and original batch allocation costs. Returns reverse their own event-date receipt amount, VAT and original allocation cost with cumulative exact reversal arithmetic. Current product department assignments classify receipts and returns, including archived products; the API and screen explicitly label this `current_product_department`, never sale-time attribution. Stock values are current business-wide balances because batches do not have branch ownership. Negative conflict batches are counted and excluded from physical valuation. Optional department/branch selections resolve only within the tenant.
- Till reports list sessions overlapping the selected Tanzania period. Journal inflows/outflows use entries recorded in the period; opening float, expected drawer, counted cash and variance cover the entire session. Cash-drop totals group handovers created in the period by their current acknowledgement status. These are internal cash transfers and never reduce revenue. Pagination is server-side.
- Damage, spoilage and wastage remove a positive exact base quantity from one selected batch. `StockService` locks the current actor/device, shop, product and batch, validates non-negative final stock and expected balance, consumes bound approval atomically, and writes exactly one append-only `stock_loss` movement. The movement stores loss category, original batch cost, whole-TSh exact loss value, product/unit and department snapshot. Encrypted reasons and public actor/approver/device IDs remain in normal history. Held/expired/inactive batches may be disposed of without altering eligibility flags; archived products remain unavailable like existing corrections.
- Loss reports count only `stock_loss` movements, grouped by damage/spoilage/wastage with snapshot department filtering and date range. General stock adjustments, stock counts, customer damaged returns and supplier returns do not become a second loss expense. The business profit summary subtracts `stock_loss_cost` once, separately from sale COGS and expense journals. Branch-sales-only reports exclude business-wide physical losses instead of assigning a fictional branch.
- Department counts select a real department/product and batch, then enter a non-negative exact physical count. Laravel computes the signed variance. Review binds operation UUID, expected batch balance, department, count and reason. Commit rechecks assignment and expected balance while locked; stale counts reject with `STOCK_CHANGED` / `DEPARTMENT_CHANGED`. Every accepted count produces one `stock_count` movement, including zero variance, retaining the counted quantity and department snapshot. Counts never bypass stockkeeper owner approval or negative-stock safeguards. This is batch-by-batch department reconciliation, with product search/keyboard-barcode entry; it is not a frozen multi-batch stocktake session.
- Loss/count UUID replay fingerprints include type/category/count/department, actor and device. Identical uncertain commits return their saved movement; changed bodies/grants cannot deduct again. Classification is part of the authoritative approval hash. UI retains the exact uncertain body in component memory and blocks cancellation until a definitive response/replay. Sign-out destroys the live workspace; no stock data or approval secrets are stored in browser storage.
- Activity alerts are owner-only persistent records. Nullable `refund_count`, `refund_amount` and `void_count` thresholds apply independently per staff member per Tanzania calendar day. Blank means disabled; there is no invented default threshold. First crossing records immutable observed value/threshold evidence, deduplicated by tenant/staff/kind/day. Owner acknowledgement retains evidence. Evaluation occurs on explicit owner refresh and `bizismart:loss-alerts` every five minutes when the scheduler runs. Configuration updates audit changed thresholds; they do not rewrite existing evidence.
- Completed receipt voids use ReturnService's explicit `operation_kind: void`, require every remaining original-line quantity and reject replacement sales. They retain the approved receipt-linked return journal and also emit one `sale_voided` audit event inside the same transaction. Financial refund thresholds include them; `void_count` counts the explicit event separately. Ordinary refunds and historical returns are never inferred to be voids, and replays do not create another event. Alert creation is local persistence, not proof that WhatsApp/SMS was delivered; F20 owns provider configuration and durable delivery.

## API additions

All paths are `/api/v1`, use the standard success/error envelope, public IDs and `no-store, private`. Read date ranges share the existing inclusive Tanzania `from`/`to` contract, maximum 366 days; paginated endpoints accept `page` and `per_page` <=100.

- `GET /reports/departments`: `from`, `to`, optional `department_id`, optional `branch_id`; returns `departments[]`, `classification`, `stock_scope`, `period`, `as_of`. Row fields: public department `id` (null for unassigned), `name`, sales/refund gross, output/refund VAT, COGS/returned COGS, net revenue/net COGS/gross profit, recorded stock value and negative batch count. The UI exports only displayed department rows; CSV explicitly records current-product classification and selected report dates.
- `GET /reports/tills`: `from`, `to`, optional branch and pagination; returns `tills[]`, standard meta, period and explicit cash/drop basis. Rows extend the established public till view with `period_cash_entries` and `period_cash_drops`. `Export this page (CSV)` exports only the fetched page, labeling session-wide drawer balances separately from period entries and handovers.
- `POST /stock/losses/preview`: `{operation_id, batch_id, qty, category: damage|spoilage|wastage, reason}`. `POST /stock/losses` uses the same fields plus review `expected_qty` and optional `approval_token` (required for stockkeepers). Quantity is a positive exact string. Preview returns the existing correction `snapshot`, `payload_hash`, `qty_after`, `approval_required` plus integer `loss_value`. Commit returns public movement, immutable loss snapshot, `replayed`, with 201 first / 200 replay.
- `POST /stock/counts/preview`: `{operation_id, department_id, batch_id, qty, reason}` where `qty` is physical non-negative count. `POST /stock/counts` adds `expected_qty` and optional approval. Same review/result contract; `snapshot.classification` includes `stock_count`, department and canonical counted quantity.
- `GET /reports/losses`: dates, optional snapshot department and category, pagination; returns `losses[]`, integer `totals` by category, record `count`, and `basis: classified_stock_loss_movements_only`. `losses[]` extend public movements with snapshot `loss`; meta is top-level. `Export this page (CSV)` exports only fetched rows, preserving exact quantities, recorded batch costs, loss value, department/reason/approver snapshots and dates. CSV buttons remain disabled while refreshing; exports reuse the established UTF-8 BOM, quoting and spreadsheet-formula protection.
- `GET /loss-alerts`: owner-only alert list, current configuration, pagination. `PUT /loss-alerts/configuration`: all three nullable thresholds, positive integer when enabled (`refund_count`/`void_count` <=10,000; value within supported exact money range). `POST /loss-alerts/refresh` evaluates today and returns newly created count. `POST /loss-alerts/{alert}/acknowledge` idempotently marks the current tenant alert reviewed.

Forbidden authority inputs include `business_id`, supplied approver/cost/loss value and calculated quantity changes. Financial reads reject cashier/manager/stockkeeper roles; stock writes preserve the existing owner/stockkeeper matrix.

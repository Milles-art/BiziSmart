# F07 — Super Admin (Filament)
**Goal:** we can onboard and manage clients without touching the database.
**Reads:** schema platform tables; product overview plans.

## Screens (Filament resources at admin.bizismart.co.tz)
Clients (create with name, subdomain, owner phone, plan), Plans, Subscriptions and payments (record payment, extend, suspend), Feature flags per client (Pennant), Users search, Client activity/health (basic). Separate `admin_users`, TOTP 2FA required, IP whitelist optional, session timeout 30 min.

## Onboarding action ("Create client")
Under D089, creates the business, default supermarket roles, main branch and selected managed subscription atomically, using the plan's explicitly configured features. Returns a private 90-minute one-use setup link through the existing owner setup flow. The owner chooses their own PIN and completes mandatory TOTP enrolment before operational access; no temporary PIN or usable owner credential is generated by the administrator. The invitation cannot reset an existing operational owner. Automatic handover messaging is not performed by this action.

## Rules
- Admin code is the only place allowed to use `withoutGlobalScopes()`; keep it inside `App\Filament\*`.
- Suspended/expired subscription -> tenant API returns 403 `SUBSCRIPTION_INACTIVE` (add to contract) except read-only login message.

## Acceptance criteria
- [ ] Creating a client produces a working subdomain login for the owner.
- [ ] Toggling a feature off makes mapped tenant endpoints return `FEATURE_DISABLED` and reports it as disabled in `/me/features`.
- [ ] Admin pages are unreachable without admin login + 2FA; tenant tokens do not work there.

## Single-product onboarding
Every client is a supermarket or mini-mart using this one product. Do not build a business-type selector or module-template system. Use the supermarket plans, roles, limits and feature flags.

## Current software contract

F20 implements the Filament client/plan/subscription/payment/feature-management page with a separate administrator guard, required authenticator MFA, persisted timestep replay protection and 30-minute idle sessions. Administrator provisioning is interactive; no operator credential is supplied by test fixtures to an operational environment. Mutations retain encrypted administrator-bound UUID/input/result evidence, refresh authority under locks and reject stale subscription revisions. Completed subscription payments are immutable records of external cash/bank/mobile payment, not transfers. Owner-authenticator recovery remains disabled by D089.

Baseline plans may be created without overwriting existing plans; features start explicitly unassigned/false until an operator selects them. Existing unmanaged local shops retain current behavior until explicitly managed. Subscription end dates are exclusive Tanzania-midnight boundaries; grace periods and automatic renewals are not inferred. TRA stays disabled until the final separately verified integration. See F20 and the shared schema/API contract for implemented fields and source boundaries. Acceptance checkboxes above remain pending the lead agent's final captured backend/browser verification; external admin domain/TLS/hosting and privately provisioned operator credentials remain deployment dependencies.
